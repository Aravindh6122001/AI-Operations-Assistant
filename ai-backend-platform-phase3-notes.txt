MONGODB — CURRENT IMPLEMENTATION

Connection / collection - PyMongo dependency is present in
requirements.txt. - MongoClient, database, and conversations collection
-> app/db/mongodb.py - Settings -> app/core/config.py and local .env -
Compound index created at startup -> app/db/mongodb.py + app/main.py -
Current index: user_id ascending, updated_at descending, _id
descending - Index supports user-specific conversation listing and the
matching sort.

Document design - Conversation document contains user_id, title,
messages array, created_at, updated_at. - Messages are embedded
documents containing role, content, created_at. - Pydantic message
validation -> app/schemas/conversation.py - BSON ObjectId is converted
to string for conversation API responses ->
app/repositories/coversation_repository.py

Conversation endpoints - POST /api/v1/conversations/ -> create - GET
/api/v1/conversations/ -> list with limit/offset - GET
/api/v1/conversations/{conversation_id} -> retrieve - PATCH
/api/v1/conversations/{conversation_id} -> update title - DELETE
/api/v1/conversations/{conversation_id} -> delete - POST
/api/v1/conversations/{conversation_id}/messages -> append message - GET
/api/v1/conversations/{conversation_id}/messages -> list messages - GET
/api/v1/conversations/stats/messages-by-role -> aggregation endpoint -
Router -> app/api/conversations.py - Business logic / ownership checks
-> app/services/conversation_service.py - MongoDB queries and
aggregation -> app/repositories/coversation_repository.py - All
conversation routes currently use hardcoded user_id=4; replace with
JWT-authenticated user ID before production.

Query operations - find/find_one -> retrieval - insert_one -> create -
update_one + $set -> title updates - update_one + $push -> append
message - delete_one -> delete - find projection excludes messages from
conversation-list results - sort + skip + limit -> paginated list -
search_by_user uses escaped case-insensitive title regex - Aggregation
pipeline -> $match, $unwind, $group, $project, $sort - Aggregation
counts messages by role for a user.

Indexes and explain - Inspect index: db.conversations.getIndexes() -
Inspect execution: db.conversations.find({user_id: 4}).sort({updated_at:
-1, _id: -1}).explain(“executionStats”) - queryPlanner -> selected plan
details - executionStats -> winning plan execution statistics -
allPlansExecution -> candidate-plan trial details - IXSCAN -> index
scan; COLLSCAN -> collection scan - nReturned -> result count -
totalKeysExamined -> index keys examined - totalDocsExamined ->
documents examined - Do not assume an index is used just because it
exists; inspect winningPlan. - COLLSCAN is not automatically bad for
tiny collections or queries returning most documents.

Atomicity / modeling trade-offs - Single-document updates are atomic. -
$push is suitable for appending embedded messages; avoid
read-modify-replace for concurrent appends. - BSON document maximum size
is 16 MiB; long histories may need a separate messages collection. -
Embed messages when they are bounded and usually read with their
conversation; use a separate collection when histories grow large or
need independent pagination/indexing. - Multi-document transactions
require suitable MongoDB deployment configuration (commonly a replica
set).
